# 3.11C Inspection — Twilio from-number resolver

**Date:** 2026-05-19
**Phase:** 3.11C-0 (blocking inspection only)
**Status:** Draft, not committed.

## Goal

Document exactly how the existing backend resolves a per-tenant WhatsApp from-number, so the 3.11 executor can reuse the same source without introducing a global `MAYA_TWILIO_FROM_NUMBER` env var.

## Source of truth (production)

**Table:** `public.agents_config` (Supabase).
**Per-channel columns:** `whatsapp_number` (WhatsApp), `phone_number` (voice). Both stored as bare E.164 strings (e.g. `+972543033010`). The `whatsapp:` prefix is **not** stored — it is added at send time.
**Identity columns:** `id` (agent UUID), `client_id` (tenant UUID), `is_active`.

## Existing send precedent (mirror, do not invent)

`app/routes/action_api.py:104` — `POST /api/actions/send-whatsapp` already implements per-tenant resolution:

```python
async def _get_agent_sender(agent_id: str) -> str | None:
    # SELECT whatsapp_number FROM agents_config WHERE id = agent_id LIMIT 1
```

The route validates Twilio credentials are present, looks up `whatsapp_number` from `agents_config` by `agent_id`, looks up the lead's `phone` from `leads`, checks the 24h window via `leads.last_whatsapp_inbound_at`, then sends:

```python
client.messages.create(
    from_=f"whatsapp:{sender}",   # sender == agents_config.whatsapp_number
    to=f"whatsapp:{phone}",
    body=req.message,
)
```

If `whatsapp_number` is empty/NULL it returns HTTP 400 `"WhatsApp sender not configured for this agent"`. **Fail-closed today.** ✅

## What 3.11 will reuse

The same lookup, normalized into `resolve_twilio_config(agent_id, client_id, lead_phone)` inside `app/services/maya_action_executor.py`. Specifically:

1. SELECT `whatsapp_number, client_id, is_active` FROM `agents_config` WHERE `id = :agent_id` LIMIT 1.
2. If row absent / `is_active=false` / `whatsapp_number` empty → `config_missing` with detail `"no_whatsapp_number_for_agent=<uuid>"`. No Twilio call.
3. **Cross-tenant safety:** if `row.client_id <> suggestion.client_id` → `config_missing` with detail `"cross_tenant_rejection"`. Defense against a future bug; not expected to trigger today.
4. Return `from_number = row.whatsapp_number` as bare E.164. The executor adds the `whatsapp:` prefix at send time, matching the action-api precedent.

## NULL `agent_id` disposition

`maya_action_suggestions.agent_id` is FK-nullable per 3.7A migration (`REFERENCES agents_config(id) ON DELETE SET NULL`). In practice every suggestion generated by `maya_action_generator` carries an `agent_id` because it inherits from the briefing's agent. There is **no documented per-client default-agent fallback** in the existing codebase.

**Decision for 3.11:** NULL `agent_id` → `config_missing` with detail `"agent_id_missing"`. We do not invent a fallback. If real production traffic ever produces a NULL-`agent_id` suggestion, the failed-card UI will surface it for triage.

## Today's failure modes that mirror our `config_missing`

| Today's behavior | Our mapping |
|---|---|
| HTTP 503 `"Twilio not configured"` (missing `TWILIO_ACCOUNT_SID`/`AUTH_TOKEN`) | `config_missing` detail `"twilio_credentials_missing"` |
| HTTP 400 `"WhatsApp sender not configured for this agent"` | `config_missing` detail `"no_whatsapp_number_for_agent=<uuid>"` |
| HTTP 400 `"Lead has no phone number"` | `missing_phone` (Class A, claim RPC handles this before we ever reach the resolver) |
| 24h-window-closed return | `session_expired` (Class A, claim RPC handles this) |

## Make.com / external config

No Make.com-only config involved. `agents_config` is the canonical store the dashboard's `/api/agents/[id]` and the backend's `agent_config.py` both read. Make.com scenarios *consume* this data via API; they do not own a parallel from-number store.

## What 3.11C must NOT do

- ❌ Introduce a `MAYA_TWILIO_FROM_NUMBER` env var.
- ❌ Copy `app/services/maya_watch.py:_send_whatsapp` (lines 922–963). That code uses the global `TWILIO_PHONE_NUMBER` env and is the **cross-tenant risk** this inspection exists to avoid. The executor MUST follow the `action_api.py` precedent, not the `maya_watch.py` one.
- ❌ Fall back to any agent's `phone_number` (voice channel) when `whatsapp_number` is missing. Different channel.
- ❌ Strip/add the `whatsapp:` prefix anywhere other than the moment of the Twilio call.

## Open questions surfaced by the inspection

1. **RLS on `agents_config`.** The existing repo contains no migration creating `agents_config` or its RLS policies (the table predates the migrations checked into this repo). All current backend reads use the service-role key. The executor will continue this pattern for the read-only from-number lookup — scoped to `SELECT whatsapp_number, client_id, is_active FROM agents_config WHERE id = :agent_id LIMIT 1`. Cross-tenant safety is enforced in Python by comparing `row.client_id` to the suggestion's `client_id` (from the claim RPC envelope), so a service-role-read does not equal a service-role-trust.
2. **`is_active=false` for an agent that owns active suggestions.** Existing `_get_agent_sender` does **not** filter by `is_active`. We will. If the agent is deactivated between approve and send, the executor surfaces `config_missing` instead of silently sending. Confirm this is the desired behavior before 3.11C coding lands — it's a deviation from the 3.10 precedent.

## Verdict

`resolve_twilio_config(agent_id, client_id, lead_phone)` is implementable safely. Source: `agents_config.whatsapp_number` keyed by `agent_id`, with cross-tenant guard against `client_id` mismatch. No global env var needed. Implementation is a 30-line function modeled on `action_api.py:_get_agent_sender` with the extra tenant check.
